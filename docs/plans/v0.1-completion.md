## Troubleshoot workflow — when manual verification surfaces a problem

Some sprint items can only be fully validated by the user (manual smoke, browser repro, hardware-dependent test). When that validation surfaces a problem after the original session has closed, the **troubleshoot agent** picks up the thread.

**Slash command:** `/troubleshoot [<sprint-item>]` (e.g. `/troubleshoot 1.3`). If no argument is provided, the agent asks which sprint command had the problem as its first question.

**Principles** (these are non-negotiable; they're integrity rules, not framing presets):

- **Agnostic on framing.** No preloaded categories ("code wrong vs world surprising vs test fake"). The diagnosis emerges from the evidence; the agent does not pick from a menu.
- **Dialogue-driven, not script-driven.** First read context, then ask the user what happened. Follow up only as evidence reveals what's relevant. Could be one question, could be many, could be zero.
- **Don't move goalposts.** Don't redefine the success criterion to make a failed result pass; don't redesign the measurement method to make it easier; don't redesign the test to fit broken code.
- **Don't fabricate evidence the user didn't provide.** Some answers only the user has (hardware, environment, what they saw, what they tried). Ask explicitly when needed and wait.
- **Diagnosis confirmed before action.** State the diagnosis as a hypothesis the user can confirm or reject; investigate further if rejected.
- **Receptive to out-of-band context.** At the start, ask: "anything you've already noticed, tried, or observed that won't show up in code or issues?" Treat any user input mid-investigation containing new context as a knowledge update, not a non-sequitur. Re-evaluate hypotheses against new evidence.
- **Mid-investigation halt is valid.** "I can't progress without X" is a legitimate pause point.

**Outputs** (only after a confirmed diagnosis and agreed fix):

- A new GitHub issue: title `troubleshoot(N.M-#<orig>): <symptom>`. Labels: `troubleshoot`, `project-honeyllm`, plus the original's bug-related labels. Body contains the original-item context, investigation findings, planned fix, and acceptance criteria. References the original with `Refs #<orig>` (never `Closes #<orig>`).
- Project board entry: `Sprint = <originating sprint>`, `Status = Todo`, `Item type = troubleshoot`, `Plan section = T<N.M>.<seq>` (e.g. `T1.3.1` for the first troubleshoot of 1.3), other fields per the originating item's tag/owner.
- Comment on the original issue: `Troubleshoot follow-up: #<new>` (does NOT reopen the original).
- Append `## Item T<N.M>.<seq>` block to the originating sprint file with kickoff prompt + validation.
- Forks the next session decision: action the fix in the same Claude session if small/well-understood, or spawn a fresh session per the session-per-item discipline.

## Spillover handling — when closing X partially completes Y

Real example from 2026-05-04: closing #236 (a troubleshooting issue) shipped the content→SW Port pattern, which **partially completes parts of #226 (logging coverage)** by adding the LogBus Port infrastructure that #226's instrumentation will write to. Without explicit handling, this kind of progress goes invisible in the plan.

**Protocol when this happens:**

1. The session that closed the spillover-source issue (e.g. #236) **must** comment on the partially-completed planned issue (e.g. #226) noting:
   - What landed: `PR #N → commit <sha>`
   - Which acceptance criteria of the planned issue are now satisfied (cite by line/checkbox)
   - What's still outstanding for the planned issue
2. Update the project board: move the planned issue to "Partially Done" status if any AC are met but not all.
3. Append a drift-log entry to the epic tracking issue's spillover log section so the next sprint's session sees it on plan-read.
4. If the spillover **fully** completes the planned item, close it normally with `Closes #<planned>` from the spillover PR — but only if every AC is met.

This is the same discipline as the existing "never close #2 from a PR" rule (memory `feedback_issue_2_never_closes.md`) extended to the spillover case: explicit prose beats inferred completion.
